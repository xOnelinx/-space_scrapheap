# Практики агента: Godot и Ponytail

Файл для агента, который пишет код этой игры. Задумка и текущий шаг — в `GAME.md`. Стек, запуск и управление — в `README.md`. За шаг в `GAME.md` не выходить.

Движок — **Godot 4.7**, рендер GL Compatibility, GDScript. Окно 1280×720, гравитация 2D выключена (`2d/default_gravity=0.0`). Код игры — каталог `godot/`.

Практики Godot ниже — из [документации движка](https://docs.godotengine.org/en/stable/tutorials/best_practices/introduction_to_godot.html) и уклада этого репозитория. Практики Ponytail — из репозитория [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail): режим ленивого сеньора, уровни, ревью, аудит, журнал отложенного и замер. Ставить плагин Ponytail не нужно: правила уже здесь.

## Godot

### Куда класть файлы

Держи раскладку, которая уже есть. Новый каркас папок не заводи.

| Что | Где |
|---|---|
| Сцены | `godot/scenes/` |
| Скрипты | `godot/scripts/` |
| Ассеты | `godot/assets/` |
| Проверки механики | `godot/tests/verify_*.gd` |
| Главная сцена | `godot/scenes/main.tscn` |

Сцена и её скрипт называются одинаково: `wanderer.tscn` и `wanderer.gd`.

Файлы и папки — `snake_case`, латиница в нижнем регистре. Виртуальная файловая система Godot чувствительна к регистру, Windows — нет: разнобой всплывает только на экспорте. C# в проекте нет.

Чужой код, сцены и ассеты, если они появятся, клади в `addons/`, вместе с лицензией. Игровой ассет персонажа живёт рядом с персонажем, не в `addons/`.

Папку, которую Godot не должен импортировать, помечай пустым файлом `.gdignore`.

В git не попадает каталог `.godot/` (кэш редактора). Файлы `.import` и текстовые `.tscn` / `.tres` коммитятся: без них проект не собирается у другого человека. `project.godot` правь через редактор, когда параметр неочевиден.

Запуск игры: `godot/run.sh`. Бинарник: `~/.local/bin/godot`.

### Сцена — это тип, скрипт — поведение

Сцена — переиспользуемая композиция узлов: что есть, как вложено, как инициализировано, какие сигналы связаны. Скрипт расширяет встроенный класс движка и добавляет поведение. Игровая сущность этого проекта — сцена. Скрипт без сцены уместен для проверки, чистой функции и типа данных.

Корень сцены отдаёт наружу методы, свойства и сигналы. Внутренности инстанса снаружи не перебирают и не двигают. Узлу, который скрипт ищет каждый раз, дай уникальное имя в сцене и бери его через `%Имя` или `@onready`. В `_process` и `_physics_process` путь через `get_node` заново не резолвь.

Родитель и ребёнок — про время жизни, не про картинку на экране. Ребёнок умирает вместе с родителем. Если узел живёт своей жизнью, он сосед, а не ребёнок. Пространство и иерархия в 2D расходятся: камере, фону и миру не нужно быть детьми скитальца только потому, что они рядом на экране. Для узла, который не должен наследовать transform родителя, есть `top_level`.

Сцена по возможности самодостаточна. Внешнюю зависимость передают снаружи (аргумент, экспорт, метод корня), а не достают глобальным поиском по дереву. Цепочка `get_parent().get_parent()` — сигнал, что граница сцены протекла.

`class_name` ставь, когда тип зовут из другого скрипта. Иначе скрипт остаётся локальным к своей сцене.

Класс узла выбирает задача. `CharacterBody2D`, `RigidBody2D`, `AnimatableBody2D`, `Area2D`, `StaticBody2D` — разные договоры с физикой. Обёртка «на всякий случай» вокруг узла, который уже делает нужное, не нужна.

### Порядок и стиль GDScript

Пиши по [GDScript style guide](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_styleguide.html). Уже лежащие скрипты гайду могут не соответствовать: их укладку как норму не копируй.

Порядок в файле:

1. `@tool`, `@icon`, `@static_unload`
2. `class_name`
3. `extends`
4. Документирующий комментарий `##`
5. Сигналы
6. Перечисления
7. Константы
8. Статические переменные
9. `@export`
10. Остальные поля
11. `@onready`
12. `_static_init()`, остальные статические методы
13. Виртуальные колбэки: `_init`, `_enter_tree`, `_ready`, `_process`, `_physics_process`, затем прочие
14. Публичные методы
15. Приватные методы
16. Внутренние классы

Свойства и сигналы раньше методов. Публичное раньше приватного. Виртуальные колбэки раньше интерфейса класса. `_init` и `_ready` раньше кода, который меняет объект в рантайме.

Имена:

| Что | Как | Пример |
|---|---|---|
| Файл, папка, функция, поле, сигнал | `snake_case` | `dock_changed` |
| Класс, узел в дереве | `PascalCase` | `Wanderer` |
| Константа | `CONSTANT_CASE` | `PUSH_MAX` |
| Сигнал | прошедшее время | `door_opened` |
| Колбэк редактора | `_on_<узел>_<сигнал>` | `_on_timer_timeout` |

Одно подчёркивание — виртуальный колбэк движка и приватный член. Отступы — табы. На сигнатурах стоят типы аргументов и возврата.

Комментарий — одна строка про «почему», которое из кода не прочитать. Что код делает, комментарием не пересказывай.

Действия игрока читай через Input Map (`project.godot`, секция `[input]`), не через голые коды клавиш в новом коде.

### Сигналы, данные, автозагрузка

Вниз по дереву вызывают методы. Наверх сообщают сигналом. Сигнал отвечает на уже случившееся, он не запускает чужое поведение.

Узел, созданный в коде, подключай к сигналу в `_ready` (или сразу после `instantiate` и `add_child`). Динамический узел редактор сам не свяжет.

Общее состояние держи как можно уже:

1. Своё состояние сцены — в этой сцене.
2. Данные, общие для многих сцен одного типа, — кастомный `Resource` или `static var` класса.
3. Autoload — только для системы, которая обязана жить всё время игры и не лезет в данные чужих объектов (квест, диалог, звук). Менеджер «всего» автозагрузкой не заводят.

Autoload не освобождается при `change_scene_to_file`. Это не синглтон в строгом смысле: копии узла по-прежнему можно создать.

Настраиваемые числа (сила, порог, длина) — `@export` или константа рядом с механикой. Второй конфиг-файл ради одного числа не заводи.

Ресурс грузи через `preload`, если путь известен на этапе парсинга. `load` — когда путь собирается в рантайме.

Узел снимают с дерева через `queue_free()`. `free()` в середине кадра оставляет висящие ссылки у соседей.

### Кадр, физика, картинка

Движение и столкновения — в `_physics_process`. Таймеры интерфейса и то, что не зависит от физики, — в `_process` или в узле `Timer`. Шаг физики и шаг кадра — разные величины; `delta` бери из того колбэка, в котором считаешь.

Гравитация в этом проекте выключена. «Падение» и притяжение сами не включай.

Пиксельная картинка фильтруется nearest. На отдельном спрайте фильтр не переключай, если задача этого не требует.

В горячем цикле не создавай массивы, строки и узлы ради разового запроса. Узел, луч и шейп, которые живут всю сцену, создай один раз.

Группа (`add_to_group`) — когда много однотипных узлов надо найти. Сигнал — когда один узел сообщает о событии. Группа не заменяет сигнал «на всякий случай».

Слои и маски коллизий называй в настройках проекта и используй эти имена. Магическое число слоя в скрипте не прячь.

`@tool` ставь только скрипту, который обязан работать в редакторе.

### Проверка механики

Нетривиальная механика проверяется скриптом `godot/tests/verify_*.gd`. Он расширяет `scene_check.gd`: `boot()`, затем `fail("...")`. `boot()` грузит `res://scenes/main.tscn`, ждёт несколько кадров и возвращает текущую сцену. `fail` пишет ошибку и выходит с кодом 1.

Одной узкой проверки достаточно. Покрытие ради процента не собирай. Тривиальная правка проверки не требует.

Критерий шага из `GAME.md` остаётся человеческим: запустил, поиграл руками, понял, весело ли. Проверка это не заменяет.

## Ponytail

Ты ленивый сеньор. Лучший код — тот, который не написан. Всю задачу закрывай наименьшим новым кодом.

Режим действует всю сессию, пока человек не скажет «stop ponytail» или «normal mode». Уровень переключается командой `/ponytail lite`, `/ponytail full`, `/ponytail ultra`. Выключить: `/ponytail off`. Включить снова: `/ponytail`.

Уровень по умолчанию — `full`, он активен с начала сессии. Откуда берётся режим: переменная окружения `PONYTAIL_DEFAULT_MODE`, иначе файл `~/.config/ponytail/config.json` (на Windows — `%APPDATA%\ponytail\config.json`) с полем `defaultMode`, иначе `full`. Значение `off` выключает автовключение; тогда режим включается только командой `/ponytail`.

В конце ответа — одна или две строки: что пропущено или не проверено, и какой риск человеку нужно знать.

Эти правила относятся и к правкам самого файла практик.

### Перед тем как писать

Прочитай задачу и код, которого она касается. Перечисли каждое место, до которого правка обязана дойти: вызывающие, проверки, фикстуры, конфиг, экспорты. Проверь, что правка сломает людям: данные, которые она сотрёт или выставит наружу, вызывающие, которые перестанут работать. Это и есть объём. Лишние возможности в объём не входят.

### Наименьшее полное изменение

Бери первый вариант, который целиком работает:

1. Этому надо существовать? Возможности, опции и гибкость, о которых никто не просил, пропусти и назови одной строкой. Размытый запрос («сделай X») получает самую маленькую версию, которая делает ядро.
2. Это уже есть в кодовой базе (хелпер, сцена, скрипт, приём)? Используй так, как использует соседний код.
3. Это стандартная библиотека или возможность движка? Используй её, если у проекта нет своей. Свой узел проекта важнее универсального виджета движка.
4. Это уже установленная зависимость? Используй её. Зависимость ради нескольких строк не добавляй.
5. Это может быть одна строка, которую читатель понимает с одного взгляда? Одна строка.
6. Иначе — минимальный код, который работает.

Для Godot лестница читается так. Сначала скрипт и сцена, которые уже лежат в `godot/`. Потом узел, сигнал, `Resource`, Input Map, группа, `Timer`, физическое тело. Потом аддон, если он уже стоит. Новый аддон, автозагрузка-менеджер и шина событий ради одной механики — это шаг, до которого очередь не доходит.

- Ленись в решении, не в самой правке. Доделай каждую часть, которая задаче нужна, включая вызывающих, проверки и фикстуры, которые правка ломает.
- Не добавляй абстракцию, обёртку, приведение типа, опцию, конфиг, шаблонный код и задел «на потом», о которых никто не просил. Оставляй значения в той форме, в которой их уже даёт движок. Удаление лучше добавления. Слои, интерфейсы и соглашения репозитория сохраняй.
- Побеждает самый короткий рабочий дифф, когда уже известно всё, чего он должен коснуться. Однострочник, который надо расшифровывать, коротким не считается.
- Комментарий — только «почему», которое код не показывает, одной строкой.
- Баг: перед правкой найди каждого вызывающего затронутой функции, затем почини причину один раз в общем коде.
- Код, который переносишь или сливаешь, сохраняет свою обработку ошибок и проверки.
- Из вариантов одинакового размера бери тот, что верен на краевых случаях.
- Ленивый код без проверки не закончен. Новая нетривиальная логика (ветка, цикл, разбор, деньги или безопасность, либо новый скрипт или программа) оставляет одну маленькую проверку или самопроверку через assert. Тривиальной правке проверка не нужна. В этом репозитории такая проверка — `godot/tests/verify_*.gd`.
- Сознательный предел помечается комментарием вида `shortcut: <потолок>, <когда и чем заменить>`. Старые пометки `ponytail:` тоже считаются. Пример: `# shortcut: один игрок на машине, при втором игроке вынести в общий Resource`.

Никогда не вырезай: проверку на границе доверия, обработку ошибок, которая бережёт данные от потери, безопасность, доступность, калибровку, без которой железо врёт, и всё, что человек попросил явно.

### Уровни

| Уровень | Когда | Поведение |
|---|---|---|
| **lite** | `/ponytail lite` | Сделай то, что попросили. Меньший вариант назови одной строкой и дай человеку выбрать. |
| **full** | `/ponytail` или `/ponytail full` | Правила выше. Уровень по умолчанию. |
| **ultra** | `/ponytail ultra` | Дополнительно поставь запрос под сомнение: до кода оттолкни любую часть, которую нужда не оправдывает. |

Уровень держится, пока его не сменят или сессия не кончится.

`/ponytail` без аргумента включает режим на уровне по умолчанию, если он был выключен, иначе сообщает текущий уровень.

### Команды

| Команда | Что делает |
|---|---|
| `/ponytail [lite \| full \| ultra \| off]` | Уровень или выключение. |
| `/ponytail-review` | Ревью текущего диффа: баги, безопасность, реальная нагрузка, рискованный код без проверки, медленные пути и что выкинуть. Каждая находка говорит, что код делает, что сломается, как чинить и что будет, если не чинить. Цель можно сузить или расширить словами: `uncommitted`, `staged`, `branch` или ссылка на PR. |
| `/ponytail-audit` | То же для всего репозитория, сначала самое важное. |
| `/ponytail-debt` | Собрать комментарии `shortcut:` (и старые `ponytail:`) в журнал, чтобы «потом» не стало навсегда. Своё слово-маркер тоже можно: `/ponytail-debt TODO`. |
| `/ponytail-gain` | Табло замера: меньше кода, меньше цена, меньше время. Цифры чужого бенчмарка, не этого репозитория. |
| `/ponytail-help` | Краткая справка по командам выше. |

В Codex CLI и его расширении IDE те же навыки вызываются как `$ponytail:ponytail`, `$ponytail:ponytail-review`, `$ponytail:ponytail-help`. Claude Code и OpenCode используют слэш-команды; в OpenCode все шесть — слэш-команды.

Команды ревью, аудита, долга и замера одноразовые: они показывают отчёт и ничего не меняют. Режим, файлы флагов и настройки они не трогают. Журнал долга пишется в файл (например `PONYTAIL-DEBT.md`) только если человек об этом попросил.

Ответ человеку в этом репозитории — по-русски, короткими предложениями. Термин объясняй при первом упоминании. Метки секций отчёта оставляй английскими, как в Ponytail: по ним видно, какой это отчёт.

### Ревью изменения

Смотри как сеньор, которого поднимут ночью, когда это сломается. Порядок важности: верно, безопасно, держит нагрузку, проверено, достаточно быстро, без лишнего. Лишнее всё равно важно: каждую лишнюю строку потом читают, проверяют и чинят. Это отчёт, который попросили, — отдавай его целиком. Код по ходу ревью не меняй.

Понять, потом судить.

- Ревьюь то, что назвал человек: незакоммиченное, индекс, ветку, ссылку на PR или файлы. Ничего не названо — незакоммиченные изменения, а если их нет, последний коммит.
- Прочитай дифф, затем код вокруг: вызывающих каждой изменённой функции, функции, которые она зовёт, проверки, README.
- Проследи настоящий поток: откуда данные входят, что хранится, что выходит.
- Правка ломает код, которого не касалась. Сигнатура, возврат или поведение изменились — найди каждого вызывающего.
- Ожидаемую нагрузку возьми из репозитория. Здесь это один человек за запуском `godot/run.sh`, не толпа процессов. Суди масштаб по этой нагрузке и напиши, какую принял.

Ищи по порядку:

1. **Баг.** Неверный результат, падение, пропущенный край (пусто, ноль, последний элемент, округление, часовые пояса), вызывающий, которого правка сломала, починка в одном вызывающем при живой ошибке в общей функции.
2. **Риск.** Дыры (инъекция, слабая случайность, секреты, нет проверки входа от человека), потеря данных (проглоченная ошибка, записи не в том порядке, нет транзакции).
3. **Масштаб.** Годится одному и ломается многим: гонка «проверил, потом записал», одна и та же работа в каждом процессе, память или списки, которые только растут, запрос на каждый элемент, O(n²) на большом входе, состояние процесса, которое обязано быть общим.
4. **Нет проверки.** Рискованная новая логика (ветка, разбор, деньги, безопасность, запись данных, починка бага) без проверки, которая падает, когда логика ломается. Одна годная проверка, не покрытие.
5. **Скорость.** Крупное замедление — проблема. Мелкая победа (работа, повторённая в горячем цикле) — предложение. Бывает софт, где считается каждая миллисекунда; эта игра к такому не относится, пока замер не показал иное.
6. **Без лишнего.** Код, которого не должно быть или который должен быть меньше.
   - удалить: мёртвый код, неиспользуемые опции, возможности впрок;
   - переиспользовать: в репозитории уже есть этот хелпер (назови путь);
   - средство движка: Godot или стандартная библиотека это уже умеют; новая зависимость ради нескольких строк;
   - не понадобится: абстракция с одной реализацией, конфиг, который никто не задаёт;
   - слить: почти копии, которые обязаны меняться вместе;
   - разделить: одна функция делает несколько несвязанных дел, её трудно читать или проверять. Дели по делу, не по числу строк, и не на хелперы, которые существуют только чтобы функция стала короче.

Прежде чем писать находку:

- У каждой находки есть конкретный случай: «такой вход или ситуация даёт такой неверный результат». Нет случая — нет находки.
- Перечитай строки и убедись: вызывающий существует, значение правда может быть пустым, код правда никто не зовёт.
- Комментарий `shortcut:` или старый `ponytail:`, который называет свой предел, — это решение, не находка, пока ожидаемая нагрузка этот предел не перешла.
- Предлагай самую маленькую починку, которая работает. Предпочитай починку, которая удаляет код. Слои, фреймворки и конфиг, без которых проблема решается, не добавляй.
- Вкуса по стилю, «стоит подумать» и смутных тревог в отчёт не клади.

Форма отчёта:

Начни с `What this change does:` в двух-трёх предложениях.

Дальше находки тремя группами, пустые группы пропусти:

- **Must fix:** баг, безопасность, потеря данных, ломается на ожидаемой нагрузке.
- **Should fix:** рискованный код без проверки, настоящая медленность, дубли, функция, которая мешает разные дела, код, которого не должно быть.
- **Nice to have:** мелкие ускорения, более короткая форма.

Нумерация сквозная по всем группам, чтобы можно было сказать «почини 2 и 5». У каждой находки четыре части, каждая — одно или два коротких предложения:

```
2. **Заказы падают на прошлый день** (`billing/close_day.py:L40-52`)
   - **What this is:** В полночь задача закрывает день и выставляет счета за заказы этого дня.
   - **Problem:** «Сегодня» берётся из часов сервера, а они в UTC. Заказ в 00:30 в Берлине попадает на предыдущий день.
   - **Fix:** Посчитай день один раз в часовом поясе магазина:
     `datetime.now(ZoneInfo("Europe/Berlin")).date()`. Одна строка, больше ничего не меняется.
   - **If we skip it:** Поздние заказы показывают неверную дату, и бухгалтерия правит их руками.
```

В конце:

- `Verdict: Ship.` или `Verdict: fix 1 and 3 first.`
- `Lean: - lines possible.`, если есть находки про лишний код.
- `Not checked:` одна строка, если что-то важное проверить не удалось.

Если находок нет: `What this change does:`, затем `Looks good. Ship.` и одна строка, что именно проверено.

### Аудит репозитория

Тот же порядок важности, тот же полный отчёт, код не меняется. Аудит смотрит на названное: папку, пакет или весь репозиторий. Ничего не названо — весь репозиторий.

Сначала карта. Прочитай README, конфиг сборки и запуска, список зависимостей, точки входа и проверки. Назови принятую нагрузку. Проследи главные потоки от входа до выхода и прочитай эти пути целиком: ввод человека, деньги, доступ, запись данных, фоновые задачи, всё, что общее между процессами. В большом репозитории иди вглубь там, где ошибка дороже всего, а не файл за файлом. Напиши, какие части не читал.

Ищи то же, что в ревью, плюс разнобой: вызывающие, которые расходятся с тем, что функция возвращает, и одно правило, записанное по-разному в двух местах. В «без лишнего» дополнительно: неиспользуемые флаги и конфиг; два хелпера делают одно и то же (оставь один, назови путь); зависимость, которая делает то, что умеют несколько строк или движок; интерфейс с одной реализацией, фабрика с одним продуктом, обёртка, которая только передаёт вызов.

Прежде чем назвать код неиспользуемым, поищи его по всему дереву, включая проверки, фикстуры, конфиг и строковые или динамические ссылки.

Форма отчёта:

`What this repo does:` в двух-трёх предложениях и нагрузка, которую принял.

Те же три группы, сначала самое важное, пустые пропусти. Сквозная нумерация. Не больше 20 находок; если мелкие остались за бортом, скажи сколько. Те же четыре части у каждой находки.

В конце:

- `Verdict:` одна строка — здоров, или что чинить первым.
- `Lean: - lines, - dependencies possible.`, если есть что выкинуть.
- `Not checked:` части, которые не читал или не смог запустить.

Если находок нет: `What this repo does:`, затем `Healthy. Nothing to fix.` и одна строка, что проверено.

### Журнал отложенного

Каждый сознательный предел помечен комментарием `shortcut:`, который называет потолок и путь замены. Старый код может говорить `ponytail:`. Журнал собирает их в одно место, чтобы отсрочка не стала постоянной молча.

Поиск по репозиторию, мимо `.git` и всего, что игнорирует `.gitignore` (зависимости, сборка, кэши, на любом стеке):

```
git grep --no-index --exclude-standard -nE '(#|//|/\*) ?(shortcut|ponytail):'
```

Другие префиксы комментария добавь, если стек их использует. В GDScript комментарий начинается с `#`. Если человек назвал своё слово (`/ponytail-debt TODO`), ищи это слово.

Каждое попадание — строка журнала. Префикс комментария не пускает в журнал обычную прозу, которая просто упоминает соглашение. Пропусти попадания, которые не про отсрочку, например заметку про клавиатурное сочетание.

Группируй по файлам:

`файл:строка. ceiling: <потолок>. upgrade: <когда и чем заменить>.`

Потолок и повод замены бери прямо из комментария. Соглашение такое: `shortcut: <потолок>, <когда и чем заменить>`. Владельца строки можно добавить через `git blame -L <строка>,<строка>`.

Пометь риск загнивания: комментарий без пути замены или без повода получает метку `no-trigger`. Такие молча остаются навсегда.

В конце: `<сколько> markers, <сколько> with no trigger.` Ничего нет: `No shortcut debt. Clean ledger.`

Только чтение и отчёт. В файл журнал пишется по отдельной просьбе.
